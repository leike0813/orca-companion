# Worker harness external evidence (remaining candidates)

Research snapshot: 2026-10-11. Bounded official help/source qualification research for the candidate set is complete; this document captures the external-source subset, not runtime acceptance. Wiki evidence is from Agent Harness Wiki release `web-v1-92e0c3b3411bc605430a21f76f793e7ea67bbbc9` (published 2026-10-09); upstream links below are official docs/source. `true` means the source explicitly demonstrates the capability, `false` means the documented interface/source rules it out for the specified implementation, and `unknown` means the checked sources do not settle it. OpenAI-compatible protocol support is not proof that MiniMax-M3.1-Flash-Preview works end-to-end.

This is evidence for the parent’s qualification decision, not a final ranking. Five user-level CLIs were installed at the parent’s request and launched in isolated Orca terminals only to observe initial readiness/auth gates; no prompt was entered and no model was called. Transcript claims concern provider/session records or explicit exports, never terminal output or streamed stdout. No database was opened.

## Eight CLI launch identity and per-run seams (versions checked above)

These facts distinguish a known ID chosen by the launcher, an ID emitted after startup, a resume selector, a real transcript source, and a hook/plugin loader. A hook receiving a session ID after a tool event is not treated as a startup identity receipt. The linked schema snippets contain no secret values.

**Historical startup observations (2026-10-11; not current qualification disposition):** On Goose's retained terminal, choosing “No telemetry” advanced startup, then the process exited with `No provider configured`; this is an absent local provider setup, not endpoint incompatibility. On Crush, choosing “Nope” at project initialization reached “Ready for instructions”; no AGENTS file was written. Vibe advanced from the welcome screen to the default `auto` theme, then reached a Mistral Studio sign-in/API-key gate; no normal provider was configured. Receipts are in `/var/tmp/ocp-next-harness-h4PUrG/terminalqualification/*-20261011.json`. Autohand's tested `--offline --bare` invocation required `AUTOHAND_API_KEY` or `auth.apiKeyHelper`. Copilot's original terminal receipt stopped at workspace trust; parent later confirmed trust accepted. Droid's fresh no-prompt trial (`term_c118f801-57f4-4b80-9f99-b31614fd912f`) used `droid --settings /var/tmp/ocp-next-harness-h4PUrG/droid-qualification/settings.json --cwd /var/tmp/ocp-next-harness-h4PUrG/project`; its overlay contained only `SessionStart`, and the native settings fields seen did not contain `customModels`. The screen required Factory account login, so authentication readiness was not satisfied. These are timestamped observations only; they do **not** establish a paid-subscription requirement, endpoint rejection, or MiniMax/Flash incompatibility. No model call was made.

## Bubblewrap seccomp and interactive terminal preservation (2026-10-11)

This section records upstream Linux/bubblewrap mechanics for the parent’s wrapper investigation; it does not prescribe or modify the local wrapper.

- **Bubblewrap interface — true:** `bwrap --seccomp FD` reads a compiled classic BPF program from an inherited file descriptor; upstream says the format is that produced by libseccomp `seccomp_export_bpf`. `--add-seccomp-fd FD` is the repeatable form for composing programs; do not combine it with `--seccomp`. Bubblewrap's parser reads the FD bytes, validates a multiple-of-8 instruction size, and installs the program with `PR_SET_SECCOMP` before running the sandbox command. Sources: [upstream bwrap manpage](https://github.com/containers/bubblewrap/blob/main/bwrap.xml), [upstream loader](https://github.com/containers/bubblewrap/blob/main/bubblewrap.c), [libseccomp BPF export API](https://github.com/seccomp/libseccomp/blob/main/include/seccomp.h.in).
- **Deny `TIOCSTI` while retaining a controlling TTY — true as a supported bwrap configuration:** bubblewrap documents that `--new-session` calls `setsid()` and disconnects the sandbox from its controlling terminal; its manpage specifically recommends a seccomp rule disallowing `TIOCSTI` when `--new-session` is omitted. Thus a caller can keep its existing terminal/session arrangement and apply a narrow filter instead. A seccomp filter matching only ioctl request values does not itself call `setsid()` or change a process group; preserve the PTY by passing the caller's stdin/stdout/stderr through and omit `--new-session`. The precise job-control behavior still depends on the launcher's existing terminal/session setup. Sources: [bwrap terminal and seccomp guidance](https://github.com/containers/bubblewrap/blob/main/bwrap.xml), [Linux `setsid(2)` semantics](https://man7.org/linux/man-pages/man2/setsid.2.html), [Linux session/controlling-terminal definitions](https://man7.org/linux/man-pages/man7/credentials.7.html).
- **Request values and narrow rule — true for Linux x86_64 UAPI:** `TIOCSTI` is `0x5412`; `TIOCLINUX` is `0x541C` in Linux's asm-generic tty ioctl header. That header notes that some architectures use different values, so build against target UAPI headers rather than treating these constants as universal. Seccomp sees `ioctl(fd, request, arg)` as syscall arguments; compare argument index 1 to the request value and return `SECCOMP_RET_ERRNO | EPERM` only for those two request codes, allowing other `ioctl`s needed by TUI/PTY operation. The kernel documents that `SECCOMP_RET_ERRNO` skips the syscall and returns the specified errno. Bubblewrap's own test demonstrates an ioctl argument-index-1 rule for `TIOCSTI`; it does not test `TIOCLINUX`, so blocking the latter is an additional narrow policy, not a claim that upstream bwrap recommends it or that it is itself a TTY-injection primitive. Sources: [Linux tty ioctl constants](https://github.com/torvalds/linux/blob/master/include/uapi/asm-generic/ioctls.h), [bubblewrap seccomp test](https://github.com/containers/bubblewrap/blob/main/tests/test-seccomp.py), [kernel seccomp return actions](https://kernel.org/doc/html/latest/userspace-api/seccomp_filter.html).
- **FD passing — true:** shell can open a precompiled filter as a chosen FD and pass that number to bwrap, e.g. `bwrap --seccomp 3 ... command ... 3<filter.bpf`. In Node, open the compiled BPF file, then use `spawn('bwrap', ['--seccomp', '3', ...], { stdio: ['inherit', 'inherit', 'inherit', filterFd] })`; `stdio` slot 3 maps the parent FD into child FD 3. Close the parent's copy after spawning. Upstream bubblewrap's Python test shows the same pattern with a temporary file, `export_bpf`, `--seccomp <fileno>`, and `pass_fds=(fileno,)`; Node's official docs specify that a positive integer in `stdio` is an open parent FD shared with the child, and that stream FDs are duplicated to their array index. Sources: [upstream bubblewrap test](https://github.com/containers/bubblewrap/blob/main/tests/test-seccomp.py), [Node `child_process` stdio](https://nodejs.org/api/child_process.html).
- **x86_64/x32 ABI handling — corrected local policy:** x32 reports `AUDIT_ARCH_X86_64` and sets `__X32_SYSCALL_BIT`. The host header `/usr/include/x86_64-linux-gnu/asm/unistd_x32.h` defines `__NR_ioctl = __X32_SYSCALL_BIT + 514` (`0x40000202`); native x86_64 `ioctl` is syscall 16. **The earlier filter that masked the x32 bit and then compared with native syscall 16 could be bypassed by x32 ioctl**, because x32's ioctl number is 514, not 16. The parent reports the corrected filter returns `SECCOMP_RET_KILL_PROCESS` for **every x32 syscall** (x32 is unsupported), and tests the x32 `bit+514` ioctl and native syscall 16. i386 has a distinct audit architecture and ioctl number 54; it remains rejected by the architecture policy unless separately implemented and tested. Sources: [kernel seccomp architecture warning](https://kernel.org/doc/html/latest/userspace-api/seccomp_filter.html), [x86_64 syscall table](https://github.com/torvalds/linux/blob/master/arch/x86/entry/syscalls/syscall_64.tbl), [x32 ABI note](https://man7.org/linux/man-pages/man2/seccomp.2.html), [upstream mixed-ABI test](https://github.com/containers/bubblewrap/blob/main/tests/test-seccomp.py); local UAPI header and filter/test result as reported by parent.
